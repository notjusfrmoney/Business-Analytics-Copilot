# Evaluation

## Benchmark contents

`questions.json` contains 27 reproducible questions based on the available sample schema:

- aggregation and simple lookup
- ranking
- comparison
- trend analysis
- multi-table joins
- target-versus-actual analysis
- root-cause analysis
- unsupported questions

Answerable questions contain `expected_sql`, written as trusted ground-truth queries. Unsupported questions contain an expected refusal reason and do not include invented schema fields. `mock_sql` and `mock_step_sql` are deterministic test-model responses used only by the no-network evaluation; they are deliberately separate from `expected_sql`.

## Ground truth and comparison

Expected rows are generated by executing each answerable question's `expected_sql` against `data/processed/business_analytics.duckdb`. The normal evaluation regenerates `expected_results.json` before running, so the expected result values come from DuckDB rather than hand-entered numbers. To regenerate them explicitly:

```powershell
python -m evaluation.generate_expected_results
```

Result comparison checks column names, row counts, cell values, and numeric values using absolute tolerance `0.01` or relative tolerance `0.001`. Row order is ignored by default; query column order is also ignored while matching values by column name. Empty results are compared explicitly.

## Run the deterministic evaluation

```powershell
python evaluation/run_evaluation.py
```

This uses deterministic test doubles for planning, SQL proposals, and answer text. It makes **no OpenRouter calls**. It evaluates generated SQL validation/execution, actual result rows against the trusted SQL result, existing answer evidence verification, expected refusals, multi-step execution on root-cause questions, LLM-call counts, SQL-query counts, and elapsed time.

The deterministic fixtures are controlled inputs to exercise the pipeline. Their scores measure pipeline and query-execution behavior for these fixtures; they do **not** estimate live-model SQL-generation or semantic-answer quality.

Output is written to:

- `evaluation/results/latest_results.json` — per-question metrics and full traces.
- `evaluation/results/latest_report.txt` — readable summary and per-question table.

The benchmark expects the current sample database at `data/processed/business_analytics.duckdb`. If it is absent, run `python tests/test_data_foundation.py` first.

## Optional live evaluation

The regular tests and deterministic benchmark do not need credentials or network access. To run five questions through the configured OpenRouter model:

```powershell
python evaluation/run_live_evaluation.py
```

Configure `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`, and optionally `OPENROUTER_BASE_URL` in `.env` first. The live runner checks configuration without printing credentials. On an HTTP 429 response it records the failure and skips remaining questions instead of repeatedly hitting the provider.

Live output is kept separately in `evaluation/results/latest_live_results.json` and `evaluation/results/latest_live_report.txt`. Provider rate limits, model availability, and model output can affect these results.

## Interpretation and limitations

- The benchmark uses the project's synthetic business dataset, not a representative production workload.
- Ground truth is deterministic SQL execution, not a model-generated answer.
- SQL/result accuracy verifies returned rows, not equivalence of SQL strings.
- Answer grounding reuses the existing numerical and evidence-content verifier. Semantic usefulness and completeness of prose are only partially evaluated.
- Deterministic results use fixed response fixtures and do not measure live hosted-model quality.
- Free hosted LLM behavior can vary; live evaluation may be affected by provider rate limits.
- Root-cause results show associations and decompositions in the supplied records. They are evidence-based analyses, not guaranteed causal inference.
- Latency is local wall-clock time from `time.perf_counter()` and includes DuckDB work plus model-response fixture or API time; it is not a production service-level measurement.

## Tests

The normal unit suite includes evaluator loading and comparison behavior plus failure-path checks for empty questions/results, unsupported questions, unknown columns, malformed SQL/plans, API errors, and a failed follow-up that retains earlier evidence:

```powershell
python -m unittest discover -s tests -p "test_*.py" -v
```
